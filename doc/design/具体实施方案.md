## 一、实施范围与完成条件

本文保留七阶段实施顺序和验收操作，并登记实施后的职责拆分与几何校正。代码与功能验收已完成；功能行为以[设计方案](设计方案.md)为准，各阶段结果见[阶段核验清单](阶段核验清单.md)。

项目名称为 **browscreen**，由 `browser`＋`screen` 组合而成。实施目标是一个 Python 3.14＋FastAPI＋Pydantic v2 服务：通过适配器连接已有浏览器，默认每 300 毫秒截图，按 `.mouse` 坐标合成指针，同一张 PNG 用于网页、图片接口和逐帧 webhook 推送；正常停止或优雅退出时清空已有 `.mouse`。首版只实现 Chrome＋CDP 适配器，端点仍从启动指定工作目录的 `.cdp` 读取。

本次预留浏览器与协议对接边界：连接、页面选择、原始视口截图及 CSS 尺寸转换归适配器；采集调度、指针合成、缓存、HTTP、webhook 和文件退出清理归公共服务。后续适配器按共同契约接入，当前不实施其他浏览器或协议。

本服务作为主服务的附属进程启动。主服务负责浏览器启动与关闭、参数设置、CDP 端口、预览 HTTP 端口、工作目录和并行环境隔离，并由主服务或外部自动化组件刷新 `.mouse`。本服务运行时只读取坐标文件进行绘制，退出时执行清空，不管理额外的坐标生命周期。

最终验收时，验证人员模拟主服务的准备动作，另外在本机启动无头 Chrome 并访问 `https://ceshiren.com`；这个测试准备动作不属于服务自身的启动功能。验收必须同时具备服务网页可见的真实网站画面、指针位置与更新检查、退出清空与同目录重启检查，以及其余功能的阶段核验记录。

首版在 `app.py` 的构造映射中登记 `chrome-cdp`，默认选择 `ChromeCdpAdapter`，并注入应用生命周期拥有的共享 HTTPX 客户端。适配器重连时只释放自身 WebSocket 与会话，共享客户端由应用退出时关闭。公共流程仅导入 `browscreen.adapters.base` 的契约和数据，不导入具体适配器；未来新增实现时修改适配器模块及集中选择处。浏览器启动和关闭始终由主服务负责。

当前实施的几何校正：Chrome 的 CSS 尺寸通过 `Runtime.evaluate` 只读获取 `window.innerWidth/innerHeight`，与不含 `clip` 的完整视口 PNG 配对；原计划的 `Page.getLayoutMetrics` 内容宽度会漏算滚动条，实测复核过程见验收记录。适配器构造映射实际位于 `app.py`。

## 三、实施步骤与阶段出口

### 阶段一：工程、环境与输入模型

1. 建立 `browscreen` 打包配置、同名 Python 包与命令入口，创建配置与请求模型。
2. 使用 `uv` 创建项目根目录 `.venv`，解析 Python 3.14 可用的依赖并生成 `uv.lock`。
3. 公共文件读取处理端点文本与 `.mouse` 单坐标对；保留不存在、为空、BOM 和有限数值校验。首版 `.cdp` 地址形式的校验交给 Chrome＋CDP 适配器。
4. 用 pytest 验证参数和文件协议，确认从项目根目录运行时可以正确导入已安装的包。

工程环境使用以下命令；本机已有 Python 3.14 时可省略解释器安装：

```sh
uv python install 3.14
uv venv --python 3.14 .venv
uv sync --python 3.14 --group dev \
  -i http://mirrors.aliyun.com/pypi/simple/ \
  --trusted-host mirrors.aliyun.com
.venv/bin/python -V
.venv/bin/python -m pytest tests/test_files_and_settings.py
```

依赖包括 FastAPI、Uvicorn、Pydantic v2、websockets、HTTPX、Pillow；初次解析后提交实际锁定版本，再以锁文件复现安装。`uv` 的源与受信任主机参数参考[官方命令说明](https://docs.astral.sh/uv/reference/cli/)，按项目约定保留上述参数形式。

阶段出口：Python 3.14 环境、`browscreen` 打包导入与入口、配置和文件读取测试均通过，记录真实版本。配置使用 `adapter` 与 `connect_wait_timeout_s`，默认适配器 `chrome-cdp`；未知名称启动失败。

### 阶段二：适配器契约与 Chrome＋CDP 连接

1. 在 `adapters/base.py` 定义 `BrowserAdapter`：端点文件名元数据和 `connect()`、`capture_viewport()`、`disconnect()` 三个异步操作，参数与输出以设计方案为准。
2. 定义 `BrowserScreenshot` 的 PNG 字节与正且有限的 CSS 视口尺寸，明确外部坐标对应同一视口。定义统一的 `BrowserAdapterError`，底层协议错误转换后交公共流程处理。
3. 实现 `ChromeCdpAdapter`，`endpoint_file_name` 为 `.cdp`：HTTP 根地址发现 `/json/version`，WebSocket 地址直接连接；浏览器级端点选择并附着首个已有页面，页面端点直接工作。
4. 在适配器内部实现命令编号、`sessionId`、事件过滤、协议错误处理、`max_size=None` 与超时；度量和 PNG 截图在同一次操作预算内完成。
5. 公共循环根据适配器元数据读取文件，调用 `connect()`，建立单调时钟截止时间；失败调用 `disconnect()` 后重新读文件，连接预算限定为 5 秒与本轮剩余等待时间的较小值。
6. 使用模拟 CDP 验证原有三种入口与异常；同时使用仅在测试中定义的 `FakeBrowserAdapter` 验证通用连接、断开、PNG 和 CSS 尺寸契约，不把测试适配器登记为产品支持项。

阶段出口：Chrome＋CDP 入口和适配器契约测试通过；缺失或错误配置可恢复，到期明确超时，不无限重置等待时间。公共流程没有 CDP 命令或具体浏览器类型判断。

### 阶段三：截图、坐标与完整帧

1. 每轮开始读取 `.mouse`，只通过 `capture_viewport(timeout_s=5)` 获取原始视口 PNG 与 CSS 尺寸；Chrome＋CDP 的底层度量与截图都封装在适配器内部。
2. 解码图片，以 PNG 与 CSS 视口的比例换算坐标；减去指针热点，使用透明叠加生成本帧图片。
3. 坐标缺失、非法或越界时返回本轮无指针的截图；每次从新截图合成，避免残影。有效坐标保持绘制，即使外部暂时不刷新也不自动过期；运行期间不改写 `.mouse`。
4. 生成包含递增编号、请求开始 UTC 时间和 PNG 字节的完整帧，一次替换缓存；按单调时钟补足目标 300 毫秒间隔。
5. 将文件读取和 Pillow 处理移到 `asyncio.to_thread`，避免阻塞 HTTP 事件循环；不重叠处理采集轮次。
6. 用有已知尺寸和标记的合成测试图片验证 1 倍、2 倍比例、小数坐标、热点偏移和边缘裁切。断言应根据独立计算的预期像素，而不是复用被测试的换算函数。
7. 用测试适配器替代 Chrome＋CDP，驱动同一公共采集、合成和缓存流程，验证指针及帧数据契约，避免通用服务绑定到 CDP。

阶段出口：可解码 PNG、热点位置、指针移除与采集调度通过测试。若目标浏览器的视口度量和截图尺寸不能形成正确映射，应先修正映射并重测，不能把偏移写成验收通过。

### 阶段四：FastAPI 与预览页

1. `lifespan` 根据 `--adapter` 创建适配器、共享 HTTPX 客户端和采集任务；启动后立即可访问 HTTP，退出时停止并等待采集任务结束，调用 `disconnect()`、关闭自身 HTTPX 连接，再尝试清空已有 `.mouse`。其他清理出错不能跳过文件清空，写入失败须记录原因；文件不存在则不创建。
2. `GET /api/screenshot` 读取一个完整帧引用，返回 PNG、帧编号、时间及 `Cache-Control: no-store`；无图片时使用 `waiting_for_browser`、`screenshot_not_ready`、`browser_wait_timeout` 通用状态码返回 `503`。
3. `GET /` 返回只读页面，以配置间隔轮询图片接口；前一请求完成后再调度，成功更新图像，失败隐藏旧图并显示状态。
4. 图片采用等比缩放；替换 Blob URL 时释放旧 URL。网页不发送操作目标浏览器的输入事件。
5. 通过接口测试确认响应契约、等待与超时状态、多调用者共享缓存；通过浏览器检查图片真实加载和轮询更新。

阶段出口：网页可显示缓存图片，接口和状态准确，增加访问者不增加 CDP 截图任务。

### 阶段五：webhook 注册与逐帧发送

1. `POST /api/webhooks` 用 Pydantic 校验 HTTP(S) 地址，规范化去重，首次返回 `201`，重复返回 `200`。
2. 新帧缓存更新后，取注册地址快照，向各地址并发 `POST` 同一份 PNG 字节及帧元数据。
3. 每个地址每帧尝试一次，限制 3 秒总耗时，不跟随重定向；记录连接失败、超时及非 2xx。
4. 等本帧发送尝试结束后再截图；慢接收方使采集降频，不建立累积图片队列。
5. 使用本地接收器保留帧编号、时间、图片哈希和结果，核对多地址、重复注册、失败隔离、慢接收方及无历史回放。

阶段出口：每张新图片均按当时唯一注册地址尝试推送，字节与帧元数据一致；发送错误不终止采集任务。

### 阶段六：失效恢复与关闭

1. 收到统一适配器错误或操作超时时，清空缓存并调用 `disconnect()`；首版覆盖 CDP 断开、协议请求超时、页面关闭或截图命令失败。
2. 建立新的恢复截止时间，从所选适配器的端点文件（首版 `.cdp`）重新读取地址，允许新地址以及原地址恢复；保留 webhook 集合。
3. 超时后停止采集和文件轮询，保留 HTTP 服务及明确错误；重启后开始新的等待。
4. 将 `.mouse` 清空放在整个服务退出流程中，已有文件截断为零字节，不删除文件、不修改 `.cdp`。CDP 断线或等待超时但服务未退出时，仍只读取坐标，不清空文件。
5. 验证正常停止及 SIGINT／SIGTERM 优雅退出时任务和连接释放、`.mouse` 已清空，连接到的浏览器仍在运行；也验证 `.mouse` 不存在时能正常退出。
6. 在外部停止写入的条件下，以同一工作目录重新启动服务，验证不出现上次指针；外部再次写入有效坐标后正常绘制。

阶段出口：等待、采集、失效、恢复、超时和关闭形成可验证的完整流程，退出清空与同目录重启检查通过，相关 pytest 均通过。主服务使用正常停止或优雅退出结束附属进程，并等待退出清理完成。

### 阶段七：本机无头 Chrome 最终验收

按下节操作执行真实验收，保存服务预览页和指针证据，逐项填写清单。最终执行全部相关 pytest；单元与接口测试通过后，仍须完成真实网站与服务页面检查。

## 四、本机最终验收操作

### 1. 准备独立验收目录与 Chrome

确认本机已安装 Chrome，验收端口可用。以下步骤模拟主服务对浏览器、参数和工作目录的准备，使用 macOS 常见 Chrome 路径、服务端口 `8000`、CDP 端口 `9222`；实施时依据本机实际情况调整并记录。本服务代码不执行这些浏览器启动与环境准备动作。

在项目根目录的终端 A 中，拟执行：

```sh
acceptance_dir=$(mktemp -d /private/tmp/browscreen-acceptance.XXXXXX)
mkdir -p "$acceptance_dir/work" "$acceptance_dir/evidence"
printf '%s\n' "$acceptance_dir"
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless \
  --remote-debugging-port=9222 \
  --user-data-dir="$acceptance_dir/chrome-profile" \
  --window-size=1280,720 \
  --no-first-run \
  --no-default-browser-check \
  https://ceshiren.com
```

终端 A 保持 Chrome 运行；在终端 B 中把 `acceptance_dir` 设为上一步输出的实际目录，然后在项目根目录拟执行：

```sh
acceptance_dir=/private/tmp/browscreen-acceptance.实际后缀
curl --fail http://127.0.0.1:9222/json/version
printf '%s\n' 'http://127.0.0.1:9222' > "$acceptance_dir/work/.cdp"
uv run --no-sync browscreen \
  --work-dir "$acceptance_dir/work" \
  --adapter chrome-cdp \
  --interval-ms 300 \
  --connect-wait-timeout-s 60 \
  --host 127.0.0.1 \
  --port 8000
```

Chrome 的无头模式和调试端口用法见[官方无头模式说明](https://developer.chrome.com/docs/automation-and-testing/headless)及[无头调试说明](https://developer.chrome.com/docs/automation-and-testing/debug-headless)。使用独立数据目录同时满足当前 Chrome 的远程调试要求，依据见[远程调试参数变更说明](https://developer.chrome.com/blog/remote-debugging-port)。以上为可复现的验收准备示例。本次使用的实际端口、工作目录和完整命令见验收记录。

### 2. 服务网页必须可见目标画面

1. 从 CDP 目标信息及页面实际 URL、标题确认被观察的页面是 `https://ceshiren.com` 对应站点，记录实际 URL 和标题。
2. 使用普通可见浏览器打开本服务 `http://127.0.0.1:8000/`。检查图片已加载、有非零自然尺寸，并在这张预览图片中识别出目标网站的实际内容。
3. 连续观察至少 30 秒，检查图片接口的不同帧编号和请求开始时间持续更新；若页面内容静止，仍通过帧编号判断采集在运行。
4. 保存一张能够识别本服务地址及网站预览内容的浏览器页面截图，并保存同一阶段的图片接口 PNG、响应头和服务日志。

只有实际服务预览页中的画面可见才满足要求。调试端口可访问、直接打开目标网站、直接下载 PNG、空白图、证书或网络错误页、验证拦截页，都不能单独认定最终通过。目标网站不可达时记录失败原因，解决后重测，不改用其他网站代替最终验收。

### 3. 指针位置、更新与移除

使用终端 C 操作同一工作目录，按顺序完成以下检查。每次操作后等到下一轮读取该文件并发布的新帧，不以仍在处理的上一帧判断失败；正常、无慢 webhook 的情况下目标更新间隔约 300 毫秒。

| 操作 | 后续验收示例 | 预期结果 |
| --- | --- | --- |
| 初始无坐标 | 保持 `.mouse` 不存在，记录基线图 | 目标网站画面中没有合成指针 |
| 写入 A 点 | `printf '320,180\n' > "$acceptance_dir/work/.mouse"` | 预览图片中出现一个指针，热点对齐 A 点 |
| 改为 B 点 | `printf '640,360\n' > "$acceptance_dir/work/.mouse"` | 指针移动到 B 点，A 点没有旧指针残留 |
| 清空坐标 | `printf '' > "$acceptance_dir/work/.mouse"` | 新帧不再绘制指针 |
| 非法或越界 | 分别写入 `abc`、`NaN,180`、`-1,180` 及 `CSS视口宽度,180` 的实际数值 | 不绘制，不沿用旧坐标，采集继续 |
| 删除坐标 | 删除仅本次验收工作目录中的 `.mouse` | 行为与清空一致 |
| 网页等比缩放 | 恢复 A 点，将预览图片宽度缩到一半 | 指针仍对齐图片中同一位置 |

A、B 点应位于实际 CSS 视口内；`--window-size` 是准备参数，不能替代实际视口和 PNG 尺寸记录。如果实际视口较小，换用视口内坐标并记录原因。

量化位置检查使用实际 CSS 视口宽高 `Wcss,Hcss`、PNG 宽高 `Wpng,Hpng`，独立计算预期热点：

```text
预期热点 = (round(x × Wpng / Wcss), round(y × Hpng / Hcss))
指针图左上角 = 预期热点 - 指针图热点
```

对 PNG 内热点检查，两个轴的偏差均应不超过 1 个 PNG 像素，并明确记录箭头热点而非图片包围框中心。网页检查以 `<img>` 的实际图片显示区域为基准，排除外层留白、边框和居中空隙，再按显示比例换算。

例如 CSS 视口 `1280×720`、PNG `1280×720` 时，A 点热点为 `(320,180)`；若 PNG 为 `2560×1440`，热点应为 `(640,360)`。当图片内容区的显示宽度为 `640` 时，两种情况下 A 点都应显示在内容区左上角往右 `160`、往下 `90` 的位置。

真实网站可能动态变化，因此跨帧全图差异不能直接归因为指针。像素级合成正确性先由固定测试图核验，真实页面再检查热点局部与服务网页的可见位置；两类证据都要保留。

### 4. 退出清空与同目录重启

1. 外部写入一个有效坐标，确认服务预览页显示指针，随后停止对该目录写入坐标。
2. 正常停止或优雅退出预览服务，保持验收 Chrome 运行；检查 `.mouse` 文件仍存在且为零字节，`.cdp` 内容未变。
3. 使用相同工作目录和参数重启预览服务，在外部未写新坐标时确认网站画面可见、没有上次指针。
4. 外部写入新坐标，确认新指针正常出现。保存退出日志、文件检查结果和重启后的服务页截图。

这些步骤只检查本服务的退出清空约定；浏览器和并行环境的启动、参数分配及回收属于主服务。

### 5. 其余功能联验与结果记录

按照[阶段核验清单](阶段核验清单.md)补齐真实 `.cdp` 缺失后写入、地址失效后更新、直接图片接口、webhook 接收和服务停止的检查。用于恢复验证的第二个 Chrome 实例，由验收准备步骤模拟主服务另行启动，使用独立数据目录和可用 CDP 端口。

验收报告保存于 `doc/project/本机验收记录.md`，证据放入 `doc/project/acceptance-evidence/`。记录环境版本、实际日期时间、命令、工作目录、尺寸、坐标、预期与实际位置、退出清空与同目录重启结果、pytest 结果、webhook 接收记录以及各项通过／失败结论。本次报告和图片均来自实际执行；验收临时目录和测试浏览器已回收。

测试结束后先停止坐标写入，再正常停止本次启动的服务并确认退出清空，最后由验收准备方停止无头 Chrome；保存证据后按需要清理独立验收目录。所有必须项通过，特别是服务网页可见目标站点、指针位置及退出清空检查通过，才可宣布后续实施完成。
