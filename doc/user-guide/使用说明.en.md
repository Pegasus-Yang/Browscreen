# User guide

[简体中文](使用说明.md) | [English project overview](../../README.en.md) | [Installation and deployment](../deployment/安装与运行.en.md)

browscreen captures the viewport of an externally managed Chrome instance, overlays the pointer from `.mouse`, and publishes one shared PNG per frame. The default target interval is 300 ms. Web preview and API readers use the latest cached frame rather than triggering additional captures.

## Browser endpoint: `.cdp`

Place `.cdp` in the directory passed to `--work-dir`. It is a UTF-8 file containing one endpoint. A UTF-8 BOM, surrounding whitespace, and a trailing newline are accepted.

| Endpoint form | Example | Selection behavior |
| --- | --- | --- |
| HTTP(S) debugging root | `http://127.0.0.1:9222` | Discover the WebSocket URL through `/json/version` |
| Browser WebSocket | `ws://127.0.0.1:9222/devtools/browser/<id>` | Attach to the first existing target whose type is `page` |
| Page WebSocket | `ws://127.0.0.1:9222/devtools/page/<id>` | Connect to that specific page |

HTTPS roots and WSS URLs are also supported. Use the actual IDs supplied by Chrome. HTTP(S) entries must be debugging root URLs, not arbitrary page URLs or `/json/version` itself. To choose a particular tab, provide its page WebSocket URL. browscreen does not open a new tab or switch automatically to the tab you bring to the foreground.

Missing, empty, malformed, or currently unavailable endpoints are retried within the startup/recovery budget. That budget ends only after the first valid frame is created. Repeated screenshot failures do not reset it. While connected and capturing normally, changing `.cdp` does not immediately switch the connection; the file is reread when recovery begins.

## Pointer position: `.mouse`

Write one coordinate pair to `.mouse` in the same directory:

```text
320,180
```

Decimal values and whitespace are accepted, for example `320.5, 180.0`. Coordinates use CSS pixels relative to the top-left corner of the current visible viewport. For desktop Chrome, the service uses `window.innerWidth` and `window.innerHeight` and maps these dimensions to the actual PNG pixel size.

For example, a 1280 × 720 CSS viewport captured as a 2560 × 1440 PNG maps `(320, 180)` to PNG position `(640, 360)`. The pointer and image scale together in the preview.

The host application controls file updates. For a manual check in another terminal, replace the example directory with your instance's working directory:

```sh
work_dir="/absolute/path/to/workspace"
printf '%s\n' '320,180' > "$work_dir/.mouse"
```

The service reads the file on each capture cycle. Valid coordinates continue to be used until the file changes; they do not expire. Missing or empty files, malformed values, non-finite numbers, and coordinates outside the viewport produce a new frame without a pointer. To remove the pointer manually, empty the file:

```sh
printf '' > "$work_dir/.mouse"
```

Graceful service shutdown also clears an existing `.mouse` while keeping the file. Reconnection and waiting timeouts do not clear it. After restarting in the same directory, write new coordinates to display a pointer again.

## Web preview

Open `http://127.0.0.1:8000/`, or the address selected at startup. The page is read-only: mouse and keyboard actions on it are not forwarded to Chrome.

Polling is sequential. Each operation has a five-second timeout covering the request, response body, and image loading. Errors hide the old image and trigger another attempt after the configured interval. Leaving the page cancels pending work; restoration from the browser's back/forward cache resumes polling.

A repeated frame ID with the same capture start time skips image reloading after the response body has been consumed. The page still accepts smaller frame IDs after a service restart. This optimization reduces image-loading work, not network transfer.

The preview's labels and status messages are currently in Simplified Chinese. The API's error codes below provide stable identifiers for integrations.

## Screenshot API

`GET /api/screenshot` returns the latest composed `image/png`. It is a viewport screenshot, not a full-page capture. Save an available frame with:

```sh
curl --fail http://127.0.0.1:8000/api/screenshot --output screenshot.png
```

| Response header | Meaning |
| --- | --- |
| `Cache-Control: no-store` | Do not cache the response |
| `X-Frame-Id` | Increasing frame number within this process; continues across browser reconnections and resets when the service restarts |
| `X-Capture-Started-At` | Start of the capture cycle as a UTC timestamp; not an exact browser-render timestamp |

If no image is available, the endpoint returns HTTP `503` and a JSON object with `code` and `message`. The message is currently Chinese. Handle the code as follows:

| Error code | Meaning and action |
| --- | --- |
| `waiting_for_browser` | Waiting for a usable endpoint; correct the file or browser state within the current budget |
| `screenshot_not_ready` | Connected, but the first valid composed frame is not ready yet |
| `browser_wait_timeout` | The startup or recovery budget expired; correct the cause and restart the service |
| `capture_failed` | The background task stopped because of an unexpected exception; inspect logs, address the cause, and restart |

After a browser failure, the old image is cleared while recovery runs. Webhook registrations remain intact. The default startup/recovery budget is 60 seconds and can be set with `--connect-wait-timeout-s`.

## Register a webhook receiver

Use `POST /api/webhooks` to register an HTTP(S) URL reachable from browscreen:

```sh
curl -X POST http://127.0.0.1:8000/api/webhooks \
  -H 'Content-Type: application/json' \
  -d '{"url":"http://127.0.0.1:9001/on-screenshot"}'
```

The first registration returns `201`; an already registered normalized URL returns `200`. The response body is:

```json
{"url":"http://127.0.0.1:9001/on-screenshot","registered":true}
```

Registrations are normalized and deduplicated, remain in memory through browser reconnections, and disappear when browscreen exits. Register them again after restarting. Invalid registration data returns HTTP `422`.

Default logs warn once for each URL's consecutive delivery failures, retain subsequent failures at DEBUG, and log recovery once at INFO. A later failure warns again. Delivery is still attempted for every frame; see the [command-line reference](../reference/命令行.en.md) to enable DEBUG logs.

For each subsequent frame, browscreen makes one concurrent `POST` attempt to each registered URL:

- The request body is the raw PNG binary data, not JSON or a multipart upload.
- `Content-Type` is `image/png`.
- `X-Frame-Id` and `X-Capture-Started-At` match the screenshot API for that same frame.
- Any `2xx` response counts as success; other statuses, connection errors, and timeouts are logged.

Your receiver should read the request body directly. For example, a FastAPI receiver can read it with `await request.body()`. Registration does not immediately replay the already cached frame or any earlier frame.

Every attempt has a three-second total timeout. Failed deliveries are not automatically retried, and redirects are not followed. Subsequent frames still receive their own delivery attempts. The next capture waits for all attempts for the current frame, so slow receivers reduce the capture rate. This guarantees an attempt for each registered address for each new frame, not successful receipt.

## Optional video recording

Install `browscreen[video]`, or use `uv sync --extra video` from source with the project's mirror options, then enable recording:

```sh
uv run --no-sync browscreen --work-dir /absolute/path/to/workspace --record
uv run --no-sync browscreen --work-dir /absolute/path/to/workspace --record \
  --record-output /absolute/path/to/recordings/session.mp4
```

Without `--record`, no PyAV dependency is loaded, recorder created, or video file written. Enabling recording without its dependencies prints an installation hint and exits with code `1`. See [optional dependency installation](../deployment/安装与运行.en.md#install-optional-video-dependencies).

`--record-output` accepts a complete `.mp4` file path, with a case-insensitive suffix. The parent directory must exist and existing files are rejected. `~` is expanded and relative paths resolve from the process working directory. This option requires `--record`. Otherwise, a unique file is created in the system temporary directory.

The MP4 uses H.264 and `yuv420p`, has no audio, and includes the pointer composed into the PNG. It reuses the capture loop's frames. The first valid frame starts the video timeline. Subsequent frames use actual capture-start timestamps, preserving delays caused by capture, encoding, or webhooks. During a browser outage, the last acquired image remains visible until recovery or capture termination; this does not establish what the browser displayed during the gap.

The first PNG's pixel dimensions determine the video canvas. Odd dimensions are padded on the right and bottom to even dimensions. Later size changes are fitted proportionally into the fixed canvas with centered black padding. Screenshot API dimensions are unaffected. Encoding uses `libx264`, `veryfast`, and CRF `18`. Each frame waits for encoding, with no accumulating queue or intentional frame dropping, so recording can reduce capture frequency and delay webhook delivery.

Send SIGINT or SIGTERM and wait for exit to flush encoding and close the MP4. Default INFO logging prints the actual absolute path, for example:

```text
录制完成，视频文件：/absolute/path/to/recordings/session.mp4
```

The completed file remains after exit. The operating system may eventually clear temporary files; select a persistent path or copy the file for long-term storage. If no valid frame was acquired, the empty file is removed and the service reports that no video was generated.

Capture timeout or an unexpected capture failure finalizes the existing video while HTTP keeps its existing behavior. Shutdown reports the partial video and reason. Runtime video-processing or write errors stop recording, attempt finalization, and report an error; screenshots and webhooks continue. Recording does not restart automatically in that run. Failed finalization reports the residual path and possible unplayability. SIGKILL, crashes, and forced interruption cannot guarantee finalization or a path summary.
